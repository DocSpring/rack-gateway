Rack Gateway uses a structured permission system based on scopes, resources, and actions.

## Permission Format

Every permission follows a three-part format:

```
{scope}:{resource}:{action}
```

**Examples:**
- `convox:app:list` - List Convox applications
- `convox:process:exec` - Execute commands in containers
- `gateway:user:create` - Create gateway users
- `gateway:deploy_approval_request:read` - View deploy approval requests

## Scopes

Permissions are organized into four scopes:

| Scope | Description |
|-------|-------------|
| `convox` | Operations passed through to the Convox API |
| `gateway` | Operations implemented within the gateway itself |
| `auth` | Authentication-related operations |
| `security` | Security-specific operations |

## Resources

### Convox Resources

Resources that map to Convox API operations:

| Resource | Description |
|----------|-------------|
| `app` | Applications |
| `build` | Docker image builds |
| `deploy` | Deployment operations |
| `env` | Environment variables |
| `instance` | EC2/container instances |
| `log` | Application logs |
| `object` | Build artifacts and objects |
| `process` | Running processes/containers |
| `rack` | Rack configuration |
| `release` | Application releases |
| `secret` | Secret env var values (`convox:secret:read` reveals them) |

The gateway forwards only the rack API routes it has a permission for (see
[Rack API Routes](#rack-api-routes)). Requests to any other route are refused with `404` and logged as denied,
whatever the caller's role, so Convox's certificates, registries, resources, instance keyroll and terminate, and
canceling an app update aren't available through the gateway (the `rack-gateway` CLI has no commands for them).
Three requests the Convox CLI makes for itself are refused without a denial entry (see
[Denied Requests](/security/compliance/audit-trail/#denied-requests)).

### Gateway Resources

Resources specific to the gateway:

| Resource | Description |
|----------|-------------|
| `api_token` | API tokens for automation |
| `audit_log` | The gateway audit log |
| `deploy_approval_request` | Deploy approval requests |
| `integration` | Third-party integrations |
| `job` | Background jobs |
| `setting` | A single gateway or app setting |
| `setting_group` | A group of settings saved together (one settings form) |
| `user` | Gateway users |

### Security Resources

| Resource | Description |
|----------|-------------|
| `secret` | `security:secret:update` refreshes the pinned rack TLS certificate |

### Auth Resources

Authentication and MFA resources:

| Resource | Description |
|----------|-------------|
| `auth` | Authentication sessions |
| `mfa_backup_codes` | MFA recovery codes |
| `mfa_method` | MFA methods (TOTP, WebAuthn) |
| `mfa_preferences` | Preferred MFA method |
| `mfa_verification` | MFA verification challenges |
| `trusted_device` | Trusted device tokens |

## MFA Requirements

Each permission also says how recently the caller must have verified MFA. A request needs the strictest level of
any permission it uses:

| Level | What the request needs |
|-------|------------------------|
| None | A signed-in session |
| Step-up | An MFA verification within the step-up window (`mfa_step_up_window_minutes`, 10 minutes by default). The CLI asks once per command |
| Step-up once enrolled | Nothing for a user's first MFA method; step-up once they have one |
| Always | An MFA proof verified on that request, even within the step-up window |

Reads and lists need none. Any other permission needs **always** unless it's listed below:

| Level | Permissions |
|-------|-------------|
| None | `convox:object:create`, `gateway:deploy_approval_request:create`, `auth:mfa_verification:create`, and the settings `ci_provider`, `circleci_approval_job_name`, `default_branch`, `github_post_pr_comment`, `vcs_provider`, `vcs_repo` |
| Step-up once enrolled | `auth:mfa_method:create` |
| Step-up | `convox:app:create`, `convox:app:update`, `convox:app:restart`, `convox:build:create`, `convox:build:update`, `convox:release:create`, `convox:release:promote`, `convox:env:set`, `convox:env:unset`, `convox:process:stop`, `convox:process:terminate`, `convox:secret:read`, `gateway:user:update_name`, `gateway:integration:create`, `gateway:integration:update`, `gateway:integration:delete`, `gateway:job:update`, `gateway:job:delete`, the `vcs_and_ci_defaults` and `session_configuration` setting groups, the settings `allow_deploy_from_default_branch`, `approved_deploy_commands`, `audit_visible_env_vars`, `circleci_auto_approve_on_approval`, `service_image_patterns`, `verify_git_commit_mode`, and the `auth` permissions other than those above and `auth:mfa_method:delete` |

So these always need MFA on the request itself: running a command in an app (`convox:process:exec`, and
`convox:process:start` except `convox run`'s placeholder start, whose command comes as an exec), deleting apps, importing builds, creating, changing, locking and
deleting users, revoking sessions, creating, changing and deleting API tokens, approving, rejecting and extending deploy approvals, removing an MFA method, refreshing the rack TLS certificate,
changing protected env vars, privileged process options, and the settings that protect secrets, loosen deploy
checks or require justifications (`mfa_configuration`, `allow_destructive_actions`, `deploy_approvals`,
`vcs_ci_deploy`, `protected_env_vars`, `secret_env_vars`, `github_verification`, `require_pr_for_branch`, and
`require_command_justification`, gateway-wide and per app).

API tokens can't verify MFA, so MFA levels don't apply to them; what a token may do is limited by its permissions and
its owner's role. The levels are defined in `internal/gateway/rbac/mfa_requirements.go`.

## Wildcard Permissions

Admin role uses wildcard permissions:

| Permission | Matches |
|------------|---------|
| `convox:*:*` | All Convox operations |
| `gateway:*:*` | All Gateway operations |
| `security:*:*` | Security operations (e.g. refreshing the rack TLS certificate) |

Wildcards match any value in that position:
- `convox:app:*` would match all app actions
- `convox:*:read` would match all read actions

<Aside type="caution" title="Admin Only">
Only the admin role holds wildcard permissions. The roles are defined in code (`internal/gateway/rbac/roles_config.go`); there are no custom roles.
</Aside>

## Permission Checking

When a request arrives, the gateway:

1. **Identifies the user** from session or API token
2. **Maps the endpoint** to a permission (e.g., `DELETE /apps/myapp` → `convox:app:delete`). Every gateway endpoint under `/api/v1` is declared in a route policy table with the permissions it needs; an endpoint that isn't in the table is refused.
3. **Checks the caller's current roles** against the required permission. Roles are read from the database on every request, so a demotion takes effect immediately. An API token must hold the permission itself *and* its owner's current role must allow it.
4. **Logs the decision** to audit trail

```mermaid
sequenceDiagram
    participant User
    participant Gateway
    participant RBAC
    participant Audit
    participant Convox

    User->>Gateway: DELETE /apps/myapp
    Gateway->>RBAC: Check permission (user, convox:app:delete)
    alt Permission Granted
        RBAC-->>Gateway: Allowed
        Gateway->>Audit: Log allow
        Gateway->>Convox: Forward request
        Convox-->>Gateway: Response
        Gateway-->>User: Success
    else Permission Denied
        RBAC-->>Gateway: Denied
        Gateway->>Audit: Log deny
        Gateway-->>User: 403 Forbidden
    end
```

| `POST /apps/{app}/builds`, `PUT /apps/{app}/builds/{id}` | `convox:build:create`, `convox:build:update` |
